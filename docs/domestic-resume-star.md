## 为什么这样选型

| 选型 | 对应的问题 | 结论与边界 |
|---|---|---|
| SQLite + 显式过滤 | 公司、城市、届别是硬约束，先过滤再排相关度 | 实测 Top20 硬条件违规为 0；未测自然语言自动抽条件 |
| BM25 + dense + RRF | 同时处理 CUDA/Qt/RTOS 等具体术语与自然语言意图 | M3 融合 nDCG@10=0.7658，对纯向量 0.6133 相对 +24.88%；对 BM25 的提升区间仍跨零 |
| BGE-M3 / small 对照 | 质量与资源成本共同决定选型 | 单岗 MRR@3 为 small 0.8750 / M3 0.8889，相对 +1.59%，CI 跨零；Recall@2 均为 0.9583 |
| Chroma 按 job_id 过滤及版本校验 | 避免相似岗位串用证据、旧索引冒充新配置 | 新旧模型独立索引，指定岗位隔离有测试 |
| FastAPI / LangChain / 智谱 | 连接数据操作、中文定性分析、材料生成 | 未进行供应商质量对照，不称智谱最优；不是每个直接接口都由 Agent 自主规划 |
| 拒答策略默认不启用 | 相似话题不一定含所问工资、年限等事实 | 阈值测试误放行 18.75% 无答案题、误拒绝 50% 有答案题，不能当可靠回答开关 |

当前 UI 默认 BM25，可切换既有 M3 语义/融合。未根据这批小样本自动更换生产 embedding。**不要写“因为 M3 全面优于 small，所以选择 M3”。** small 融合 nDCG@10=0.7867、Recall@20=0.7831，均高于 M3 融合；M3 融合 MRR@10 较高。合理表述是实现可切换策略，以业务指标和资源约束选型，保留小模型备选。当前只使用 dense，没有 M3 稀疏/多向量能力。

## STAR 讲述（约 90 秒）

**S：** 国内校招岗位分散在官网和公告里，城市、届别、技能要求表达不统一，求职者需要反复读 JD、对照简历、准备材料。

**T：** 我希望打通简历导入、岗位发现、证据分析、草稿生成和投递追踪，并证明检索方案在具体任务上是否有效，不能只报接近满分的 Recall。

**A：** 我用 FastAPI、SQLite 和 LangChain 实现工作流，用 Chroma 的岗位过滤限制证据来源。发现旧评测多数岗位不足 5 个片段，Top5 Recall 容易饱和后，将任务拆成全库找岗位、单岗找证据和资料缺失识别。冻结真实国内 JD，加入多条件、数值、否定和优先项问题，对照 small、M3、BM25 与 RRF。逐题核查发现同义漏标，保留旧结果、修正标签后重跑，明确这是回归评测。

**R：** 在 267 岗位自建约束银标集的 18 个有答案搜索测试题上，M3 融合对纯向量将 MRR@10 从 0.6765 提到 0.8385，Recall@20 从 0.6562 提到 0.7658。但 M3 对 small 的单岗 MRR 提升仅 1.59%，区间跨零，small 融合的部分全库指标更优。因此成果是业务检索策略和评测链路得到改进，不能声称大模型全面胜出或真实面试通过率提升。

## 面试追问

- **是严格评测吗？** 公式、冻结、隔离索引、分组和阈值隔离更规范，任务更贴近使用；仍缺独立人工标签和新用户盲测。80 题由助手按原文编写，搜索为条件银标，不称工业级金标。
- **为何不继续写 0.9963 Recall？** 旧同岗 Top5 候选池太小，随机期望已接近 1。现在测全库 Recall@20、单岗 Recall@2 和完整支持率，并保留无答案题。
- **为什么不选 small？** 证据支持保留 small 为低资源备选，不能强行证明 M3 值得全部额外成本；正式迁移需更独立标签和资源验证。
- **1024 长度提升多少？** M3 512 与 1024 主指标相同，只证明减少截断，没证明提升质量。
- **能商用上线吗？** 个人 MVP 核心闭环、正式库和新搜索接口已验证；多用户授权、容器实机、压力恢复、生成事实性和长期稳定性仍未完成验收。不能写成已完整公网商用上线。

项目价值在业务闭环、任务拆分、检索策略与可复现诊断，不能靠挑选一个漂亮分数证明模型最优。
