# 输出契约

按任务选择最小充分输出，不把一份材料扩展成用户没有要求的整套申请包。

## 通用状态字段

在结构化响应中优先提供：

- `status`：如 `ok`、`needs_jd`、`draft`、`generated_not_submitted`、`error`。
- `stage`：如 `intake`、`evidence_collected`、`job_resolved`、`analyzed`、`generated`。
- `evidence_level`：`verified_profile`、`user_provided` 或 `missing`。
- `contact_status`：`confirmed`、`partial` 或 `pending_confirmation`。
- `missing_fields` 与 `next_action`：指明可补充信息和下一步；`result` 可保留给旧前端展示。

## 匹配分析

使用以下层级，并让每个候选人事实可回溯到候选人资料、用户当轮文本或精确 JD：

1. `## 匹配分`：仅在精确 JD 与候选人证据均可用时给出 0–100 的证据加权判断；不表示录用概率。
2. `## 匹配证据`：候选人证据与岗位要求成对陈述，并标明证据等级。
3. `## 主要短板`：缺少、未验证或需要补充的要求；不写成候选人失败事实。
4. `## 简历优化建议`：可执行改写建议，明确哪些信息需确认。
5. `## 可用于投递的关键词`：仅使用 JD 或已有候选人资料支持的关键词。
6. `## 面试风险点`：说明需要准备的证据与追问方向。

若个人证据为 `missing`，省略匹配分和个人匹配断言，改为“通用准备建议”。结尾说明：`来源说明：分析基于候选人资料、用户当轮文本与知识库中的公开历史岗位描述或用户上传 JD；职位当前开放状态以官方渠道为准。`

## 定制材料

| 产物 | 约束 | 必含状态 |
|---|---|---|
| 求职信 | 500–800 字；专业、克制、具体；仅使用可追溯事实 | `draft` + `evidence_level` |
| 投递邮件 | 包含主题和正文；正文不超过 500 字；说明附件但不声称已发送 | `draft` + `contact_status` |
| 面试准备 | 高频技术问题、项目深挖、反问问题；个人项目题须有证据来源 | `draft` + `evidence_level` |
| 申请包 | 匹配报告、求职信、面试题、邮件草稿及本地输出路径 | `generated_not_submitted` + `contact_status` |

联系人信息缺失时，邮件正文和签名使用“姓名/邮箱/电话：待确认”；申请记录保留缺失字段，绝不填充示例值。

## 证据标签

- **已验证证据**：来自 `candidate_profile` 或精确 JD 的受控检索片段。
- **用户提供证据**：用户当轮明确提供的简历、项目或联系方式文本。
- **推断**：由两个或多个证据得到的判断；使用“表明”“可能匹配”等限定语。
- **待补充**：没有证据支持的指标、规模、成果、技术职责或联系人字段。
- **建议**：为补齐差距而提出的行动，不描述为既有经历。

## 交付收尾

说明已生成内容、证据等级、联系人状态、缺失项和下一步。例如：

`状态：generated_not_submitted。候选人证据：user_provided。联系人：pending_confirmation（姓名、邮箱、电话待确认）。材料已生成到本地；请确认联系人信息后再发送。`
